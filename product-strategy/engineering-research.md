## Parallelization Analysis

The proposal's data model constrains parallelization more than file layout because there are no files yet. The major shared schema/API conflicts are:

- `GraphStore` schema and migration files: every slice eventually depends on the same SQLite database, so independent migrations touching `GraphNode`, `NodeRevision`, `GraphSnapshot`, `WorkingSetSnapshot`, `OptimizerEdit`, `ConflictRecord`, or `AuditEvent` will conflict unless schema ownership is explicit.
- `RenderEngine`: VS-001, VS-002, VS-004, VS-005, VS-006, VS-007, VS-008, VS-014, VS-015, and VS-017 all affect render inputs or labels.
- `PolicyEngine`: summary gates, budget gates, provider gates, graph-action allow/deny sets, worker write-scope gates, and recovery gates are one shared API surface.
- Snapshot-walk-then-merge: foreground `GraphAction` is restricted to evidence/tool/audit/output/advisory request effects (`proposal.md` lines 473-511), while `OptimizerEdit` alone mutates summaries/topology/identity (`proposal.md` lines 691-718). Any parallel work that blurs this boundary creates a semantic conflict even if files differ.
- Append-only `OptimizerEdit`: VS-010, VS-011, VS-012, VS-013, VS-014, VS-018, and VS-019 share optimizer edit lifecycle and merge validation.
- Worker overlap policy: VS-015, VS-017, VS-018, VS-020, and VS-021 share `WorkerSlice`, `WorkerRun`, `QuestionArtifact`, `RecoveryAction`, and child acceptance semantics.

## Technical Constraints Summary

- **Local state is canonical.** The harness graph, evidence storage, and audit trail must live under local filesystem/SQLite control; agent-runner state and CLI transcripts are evidence sources, not canonical graph truth. Evidence: `product-strategy/philosophy.md` lines 145-153 and `product-strategy/proposal.md` lines 112-123.
- **No in-product compaction.** `/compact` and auto-compaction are treated as corruption or prevented by render discipline. Claude Code auto-compact around high capacity is explicitly called out as platform reality. Evidence: `product-strategy/philosophy.md` lines 85-91 and 193-197; `product-strategy/proposal.md` lines 83-86 and 1444-1455.
- **CLI process lifecycle is asymmetric.** Interactive REPL uses TTY pass-through; one-shot runs use prompt payloads; stdout must remain model output while invocation metadata appears on stderr. Evidence: `/home/nes/projects/agent-runner/README.md` lines 106-139, 182-200, 338-354.
- **Resume is not uniform.** Claude uses flag-style resume; Codex uses subcommand-style resume; child acceptance is not guaranteed by recording an attempted resume. Evidence: `/home/nes/projects/agent-runner/README.md` lines 416-476 and local `~/.config/oulipoly-agent-runner/models/claude-opus.toml`.
- **Claude `--session-id` capture is stronger than Codex rollout capture.** agent-runner documents forced Claude session IDs with stream-json readback, while Codex parses `thread.started` from JSON mode. Evidence: `/home/nes/projects/agent-runner/README.md` lines 384-415.
- **Opencode has weaker current ingestion substrate.** The problem statement says opencode uses SQLite and plugin transforms, but raw DB hot edits are unsupported and opencode turn ingestion is not configured locally. Evidence: `product-strategy/problem.md` lines 71-75 and 159-165; local `~/.config/oulipoly-agent-runner/sessions.toml`.
- **Provider quota windows are substrate state, not complete budget state.** agent-runner handles provider quota projections and exhausted accounts; harness still needs per-render, per-worker, per-optimizer, and per-reviewer `BudgetLedger`. Evidence: `/home/nes/projects/agent-runner/README.md` lines 202-220; `product-strategy/proposal.md` lines 825-846.
- **Prompt-cache economics constrain render churn.** Cache prefix hashes are part of `WorkingSetSnapshot` and `BudgetLedger`; optimizer edits that rewrite stable prefixes can create cost regressions. Evidence: `product-strategy/problem.md` lines 129-137; `product-strategy/proposal.md` lines 438-472 and 825-846.
- **Snapshot-walk-then-merge is pervasive.** Orchestrator turns read stable `GraphSnapshot`; optimizer edits merge only after turn boundaries; conflicts fail closed. Evidence: `product-strategy/proposal.md` lines 30-35, 290-317, 1052-1082.
- **Foreground graph actions are intentionally narrow.** `GraphAction` may record evidence/tool/audit/output/advisory optimizer requests, but cannot mutate nodes, edges, revisions, summaries, identity, topology, provenance repair, or quarantine. Evidence: `product-strategy/proposal.md` lines 473-511 and 983-991.
- **Worker output is staged, not trusted.** Worker final output becomes evidence, candidates, conflicts, questions, and advisory optimizer requests; workers do not directly mutate graph truth. Evidence: `product-strategy/proposal.md` lines 1083-1116.
- **MCP is portable but insufficient alone.** The harness must combine MCP with hooks, plugin transforms, wrapper staging, and possibly headless APIs because MCP cannot impose per-turn context by itself. Evidence: `product-strategy/problem.md` lines 71-75; `product-strategy/proposal.md` lines 62-70.
- **Tauri desktop scope excludes server assumptions.** The app is single-user, single-tab, one orchestrator; no multi-tenant auth, cloud deployment, or team access-control matrix exists in scope. Evidence: `product-strategy/philosophy.md` lines 155-163 and `product-strategy/proposal.md` lines 1436-1458.
- **Tauri Linux system dependencies are present locally, but the harness has no scaffold.** Agent-runner documents WebKit/GTK prerequisites, and this machine has those packages installed; `agent-harness` still lacks `src-tauri/` and package metadata. Evidence: `/home/nes/projects/agent-runner/README.md` lines 11-18 and `product-strategy/proposal.md` lines 14-21.
- **SQLite CLI availability cannot be assumed.** The local `sqlite3` shell is absent, while agent-runner uses bundled `rusqlite`. Harness diagnostics/tests should use Rust/database APIs or add the CLI explicitly. Evidence: `/home/nes/projects/agent-runner/src-tauri/Cargo.toml`.
